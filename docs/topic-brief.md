# 題材企画: アプリケーション生成 UUID が新規集約を既存扱いにする問題

## 対象

| 項目 | 内容 |
| --- | --- |
| 対象言語 | Java 21 |
| 対象読者 | Java、Spring Boot のテスト、および Spring Data JDBC の基本的な Repository 利用を理解している開発者 |
| 難易度プロファイル | 実践・上級 |
| 選定理由 | ID を先に生成する設計と永続化フレームワークの状態判定が相互作用するため、単純な構文の問題ではなく、実務で見落としやすい境界条件を扱えます。 |
| 実行基盤 | Maven 3.8 以降、Java 21、Spring Boot 3.4.4、Spring Data JDBC、H2、JUnit Jupiter |
| フレームワーク依存性 | 本ラボはユーザー指定の Spring Data JDBC 固有の状態判定を題材にします。そのため、フレームワーク非依存の題材としては扱いません。 |

## 学習する契約

> アプリケーションが UUID を設定して作成した新規の `WorkItem` を `CrudRepository.save` に渡した場合、期待する状態は 1 件の行が INSERT されて再読込できることですが、バグ状態では既存集約向けの UPDATE が 0 行を対象にして例外になります。

### 対象の直接原因

`@Id` が非 `null` であることを既定の new 判定に委ねているため、実際には未保存の集約が既存扱いになります。`@Version` が `null` の新規状態を明示していません。

### 対象外

このラボでは UUID の衝突、DB 側の UUID 生成、複数集約の保存順序、Web API、トランザクション分離、楽観ロックの競合処理は扱いません。`Persistable` や `JdbcAggregateTemplate.insert` は代替策としてのみ記録し、修正対象にはしません。

## 再現設計

| 要素 | 決定 |
| --- | --- |
| 公開境界 | `WorkItemRepository.save(WorkItem)` |
| 入力・初期状態 | `WorkItem.create("再現用の作業項目")` で生成した UUID を持つ新規集約と、空の H2 テーブル |
| Red の観測 | 保存が例外を投げないことを求めるアサーションが、Spring Data JDBC の 0 行更新例外で失敗します。 |
| 最終観測 | 修正後に `findById` で独立に再読込し、タイトルと行数を確認します。 |
| 決定性 | H2 のインメモリ DB とテストごとの DDL 初期化だけを使用し、時刻・乱数の値そのものには依存しません。 |
| 固定状態の検証コマンド | `mvn test` |
| バグ状態の確認コマンド | `mvn -Dtest=WorkItemRepositoryTest test` |

## 仮説

| 仮説 | どう検証または除外するか |
| --- | --- |
| 主仮説: 事前設定した UUID により新規集約が UPDATE 対象と判定される。 | バグ状態の例外を観測し、`@Version` を `null` とする新規状態を明示した修正後に同じテストが成功することを確認します。 |
| 競合仮説: H2 の UUID 型またはスキーマ定義が保存を拒否している。 | UUID をパラメータに取る UPDATE が実行され、修正後は同一スキーマで INSERT と再読込が成功することを確認します。 |
| 競合仮説: テストのトランザクション境界が読込不能の原因である。 | 同じ `@DataJdbcTest`・同じスキーマで、修正後に Repository の再読込が成功することを確認します。 |

## 予定する履歴

| 順序 | コミットの目的 | 期待する状態 |
| --- | --- | --- |
| 1 | アプリケーション生成 UUID の保存失敗を再現する | 対象テストが意図した 0 行更新例外で失敗します。 |
| 2 | UUID を持つ新規集約の状態判定を修正する | 同じテストと全体テストが成功し、行が再読込できます。 |
